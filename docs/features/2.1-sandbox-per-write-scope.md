# 2.1 One container sandbox per write scope

**Phase 2** · **Status: In progress. The spike is done and `read-only` and `artifacts` have a Docker profile behind an opt-in flag.**

## User story

As a **operator** I want **each run to execute in a container whose reach matches its write scope** so that **a read-only agent provably cannot read secrets, write or push, whatever it tries**.

## Issues

- [#21](https://github.com/iwerksom/agent-runner/issues/21) One container profile per write scope, no credentials at read-only (open)
- [#35](https://github.com/iwerksom/agent-runner/issues/35) Solo mode: the sandbox, not auth, releases working-tree and draft-pr (open)

## Acceptance

- `read-only`: worktree mounted read-only, no network except the gateway, no credentials. `artifacts`: one writable output directory. `working-tree`: writable worktree, no credentials. `branch-push` and up: a forge token scoped to one repo.
- Reads are confined to the worktree, including Bash operands (the gap left in 2.2).
- In solo mode a held tier is runnable once its sandbox profile exists; outside solo mode the hold still needs auth (#35).

## Notes

The gate in `writeScope.ts` stays as a second layer after this lands.

## Design proposal (draft 2026-10-02, backend decided: Docker)

### What is true today (checked against the code and this machine)

- The Claude Code process is started by the SDK with **no `env` option**, so it
  inherits the whole console environment: `ANTHROPIC_API_KEY`, `DATABASE_URL`, and
  anything else exported. Its `HOME` is the operator's, so `~/.ssh`,
  `~/.config/gh` (the `gh` login) and `~/.claude` (user-level skills, #15) are all
  reachable.
- One process does everything: the `Read` and `Grep` tools, `Bash` commands, and
  the repo's own hooks from `.claude/settings.json` (loaded because
  `settingSources` is `["project"]`; hooks run outside the permission gate). So a
  sandbox has to wrap the **whole process**, not just Bash.
- `canUseTool` is advice, not a boundary (DECISIONS #22). The gate now confines the
  structured read tools and refuses `.env`, but Bash operands of allow-listed
  programs can still read any path (#27).
- A leased worktree is a `git worktree`: its working files are in
  `workspaces/worktrees/<id>`, but its git admin directory (index, HEAD) is
  `<mirror>/worktrees/<id>`, and objects and refs are in the bare mirror.
- This machine (WSL2, Ubuntu 24.04, systemd on, no Docker Desktop on the Windows
  side): **Docker is not installed yet**, and `sudo` needs a password. The Claude
  Code binary is one dynamically linked native executable.
- The SDK offers two hooks for this: `spawnClaudeCodeProcess` ("run Claude Code in
  VMs, containers or remote environments") and a built-in `sandbox` setting that
  covers **Bash commands only**.

### The shape

A **sandbox profile** is compiled from the manifest's `writeScope` into four
things: filesystem mounts, environment (credentials), network, and a writable
output. A **sandbox backend** takes a profile and wraps the `claude` process
through `spawnClaudeCodeProcess`. The runner depends on the profile and a small
backend interface, never on Docker directly. **The backend is Docker**, for solo
use now and for the hosted deployment later (Phase 8), so the sandbox you build
and learn on here is the one the team deployment runs.

| Write scope       | Filesystem                                                                                                             | Environment and credentials                                                    | Network                                        |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------- |
| `read-only`       | worktree read-only; mirror read-only; empty temporary `HOME`; system directories read-only                             | the model API key only; a read-only forge token only if the manifest uses `gh` | model API (and the forge host if `gh` is used) |
| `artifacts`       | as `read-only`, plus the directories named by `artifactGlobs` writable                                                 | as `read-only`                                                                 | as `read-only`                                 |
| `working-tree`    | worktree writable; the worktree's own git admin directory writable (git needs its index); rest of the mirror read-only | as `read-only`, no forge token                                                 | as `read-only`                                 |
| `branch-push`     | as `working-tree`, mirror writable                                                                                     | plus a forge token scoped to one repo                                          | plus the forge host                            |
| `draft-pr`        | as `branch-push`                                                                                                       | plus PR-create permission on that token                                        | as `branch-push`                               |
| `external-writes` | as `draft-pr`                                                                                                          | plus tracker tokens                                                            | plus tracker hosts                             |

Credentials stop being inherited: the runner passes an **explicit `env`** built
from the profile. That step needs no sandbox backend and can ship first.

### Backend: Docker (decided 2026-10-02)

Docker (a container around the whole `claude` process) was chosen over
bubblewrap and over Claude Code's built-in `sandbox` setting. It confines the
Read tool, Bash and the repo's hooks alike, it controls the network, and it is the
same sandbox in the hosted deployment (Phase 8). The built-in setting only covers
Bash, so it can at most be an extra layer. Bubblewrap would have been lighter on
this machine but would have been replaced when Arnold is hosted.

### Docker specifics

- **Image:** a small image (Ubuntu 24.04, the same libc family as the host) with
  `git`, `gh`, `ripgrep` and the shell tools the allow-lists use. Per-repo
  toolchains (Node, Python) come later as extra image layers or variants. The
  `claude` binary is bind-mounted read-only from the SDK's `node_modules`, so its
  version always matches the pinned SDK; a hosted image bakes it in instead.
- **Started through `spawnClaudeCodeProcess`** as `docker run --rm -i ...`: the SDK
  talks to the process over stdin and stdout, which `-i` passes through. The
  container is named per run, and cancellation stops it.
- **Same absolute paths inside and outside.** The worktree and the mirror are
  mounted at the same paths they have on the host, because a git worktree records
  absolute paths to its admin directory, and transcripts and provenance would
  otherwise disagree about where files are.
- **Runs as the host user** (`--user uid:gid`), so nothing in the worktree becomes
  root-owned.
- **Hardened by default:** `--read-only` root filesystem with a `tmpfs` for `/tmp`
  and `HOME`, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--pids-limit`,
  `--memory` and `--cpus` limits, and a wall-clock timeout that also stops the
  container.
- **Credentials by `--env-file`**, written to a temporary file with mode 0600 and
  deleted as soon as the container has started, rather than `-e KEY=value`, which
  shows in `docker inspect` and the process list.
- **Network:** the default bridge for now (the model API must be reachable). With
  the gateway (Phase 4) the sandbox joins a network whose only exit is the gateway.

### What this does not solve

- **The model API key is still inside the sandbox**, in the process environment, so
  a compromised agent could read it. Only the gateway (Phase 4, feature 4.2) fixes
  that, because the run then holds a capped virtual key instead.
- **Network stays open in Phase 2.** Restricting egress to a single target is
  trivial once the gateway exists (Phase 4) and awkward before it, so this phase
  confines files and environment and leaves egress to Phase 4. Until then the gate
  and the allow-list remain the only egress control.
- **Docker must be installed** on whatever runs the worker. On this machine it is
  not yet (see the first decision below).

### Build plan

Each step ships on its own and is checked by a smoke assertion that an attempt to
read a secret from inside the sandbox fails.

1. **Docker on this machine, and a spike (about a day).** Install Docker, build the
   image, and run `sandbox-doc-drift` end to end through `spawnClaudeCodeProcess`.
   Output: the exact mounts needed, whether the SDK accepts a container process,
   and a DECISIONS entry (the same shape as the harness spike).
2. **Explicit environment.** Replace the inherited environment with a profile-built
   one: no container needed, removes `DATABASE_URL` and stray tokens from every run.
3. **Profile compiler and the Docker backend for `read-only` and `artifacts`.**
   Smoke: `~/.ssh`, `.env.local` and a path outside the worktree are unreadable,
   including through Bash operands. This closes the remaining gap on #27. An empty
   `HOME` also keeps user-level skills out of runs (#15).
4. **`working-tree` and `branch-push` profiles**, including the git admin directory
   mounts.
5. **Solo-mode setting and a startup self-test.** A tier is released (#35) only
   when its profile exists and the self-test, which tries to read a canary secret
   from inside a container and must fail, passes. Update the held manifests and
   smoke [13].

### Progress

- **Step 1 (spike): done.** Result in DECISIONS #29. A sandboxed `sandbox-doc-drift`
  run succeeded and cancelling stops the container.
- **Step 2 (explicit environment): done inside the sandbox.** The container gets an
  allow-listed environment; runs that are not sandboxed still inherit the whole
  console environment.
- **Step 3 (profile and Docker backend for `read-only` and `artifacts`): built**,
  opt-in with `ARNOLD_SANDBOX=docker` (`packages/core/src/sandbox.ts`, image in
  `sandbox/`, `pnpm sandbox:build`). Smoke [20] covers the profile logic without
  Docker. Not yet verified: an `artifacts`-tier agent end to end, and a Bash
  operand read of a secret from inside the container as part of a smoke check.
- **Steps 4 and 5:** not started.

### Decisions

1. **Backend: Docker. Decided.**
2. **Install Docker in WSL.** Needs you, because it needs `sudo`; the commands are
   in the PR description. Docker Desktop on the Windows side is the alternative, but
   the engine inside WSL is simpler for this setup and teaches more.
3. **Read-only forge access (open).** The scoper uses `gh issue view`. With an empty
   `HOME` it can no longer see your `gh` login. Recommended: a fine-grained
   read-only token in an environment variable for the agents that need `gh`.
4. **`artifacts` tier (open).** Recommended: mount only the directories its globs
   name (safest, but they must exist first) rather than the whole worktree writable.
5. **Network (open).** Recommended: accept an open network in Phase 2 and close it
   with the gateway in Phase 4.

### Acceptance (from the roadmap)

- A `read-only` or `artifacts` run has no push credential and no forge token in its
  environment.
- Reads are confined to the worktree, including Bash operands.
- A solo-mode setting releases a tier once its profile exists.

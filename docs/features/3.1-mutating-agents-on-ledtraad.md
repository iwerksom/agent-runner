# 3.1 Mutating agents on ledtraad

**Phase 3** · **Status: Planned**

## User story

As a **maintainer of ledtraad** I want **to add the existing agents to ledtraad as the work in each phase unblocks them** so that **each agent is available on ledtraad as soon as it can run there safely, and I never have to wonder which ones are ready**.

## How agents are added

An agent is added to ledtraad by writing its binding under `registry/ledtraad/` (the prompt is shared; only the repo's values and allow-list differ, as `doc-drift` already does), syncing the registry, and making a first run. It is added when its blockers below have closed, and not before. Until 6.2 (Phase 6) there is no console flow for this: it is a small code change per agent.

## Decided 2026-10-05: a repo's toolchain is a layer on the base image (#66)

`sandbox/images/<slug>.Dockerfile` extends `arnold-sandbox:dev` and is built as
`arnold-sandbox-<slug>:dev` by `pnpm sandbox:build`; a repo with no such file runs in
the base image. The profile picks the image from the repo's slug (`sandboxImageFor`),
and the canary self-test runs on that image, cached per scope and image.

ledtraad's layer (`sandbox/images/ledtraad.Dockerfile`) carries what its static CI job
installs: Python 3.12, FastAPI, pydantic, numpy, httpx, anthropic and pyflakes. Checked
in the container against a ledtraad checkout: the API imports, `test_reports.py`,
`test_query_stream.py` and `validate_json.py` pass, pyflakes and `bash -n` are clean.
What it cannot do: anything needing `data/` (the 299 MB corpus is not in git, per
`docs/DATA.md`), the `.venv`, torch or the pipeline stack, so the golden set and the
location tests are out of reach and a run must report them as not run.
